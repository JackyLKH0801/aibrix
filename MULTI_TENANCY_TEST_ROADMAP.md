# AIBrix Multi-Tenancy Testing Roadmap & Guide

This document outlines the strategy for testing multi-tenant isolation in AIBrix, confirming that different tenants can securely access their specific Low-Rank Adapter (LoRA) models while being blocked from accessing others.

## 1. Architecture Overview
AIBrix achieves multi-tenancy using **Header-Based Routing** via Envoy Gateway.
- **Components**:
  - `ModelAdapter`: Defines the LoRA adapter and isolation policy.
  - `HTTPRoute`: Generated by the controller, maps HTTP requests to the correct adapter service.
- **Routing Logic**:
  - Requests must include a matching `model` header (the adapter name).
  - For isolation, requests must *also* include a `x-aibrix-tenant-id` (or `x-tenant-id`) header matching the tenant's ID.

## 2. Test Environment Setup
### Prerequisites
- Kubernetes Cluster (e.g., Minikube).
- AIBrix installed (Controller, Gateway).
- vLLM Runtime running a Base Model (e.g., `qwen2.5-1.5b-instruct`).

### Resource Configuration
To enable isolation, `ModelAdapter` resources must be labeled correctly.
**Example (Tenant A):**
```yaml
apiVersion: model.aibrix.ai/v1alpha1
kind: ModelAdapter
metadata:
  name: qwen-code-lora-tenant
  labels:
    # Required for routing
    model.aibrix.ai/name: "qwen-code-lora-tenant"
    # Required for isolation (MUST match the header value)
    tenant.aibrix.ai/id: "tenant-a" 
spec:
  isolationPolicy:
    strategy: "namespace"
    namespace: "tenant-a"
  # ... other specs ...
```

## 3. Testing Roadmap
### Phase 1: Deployment Verification
- **Objective**: Ensure adapters are loaded and services utilize the base model.
- **Action**: Check `kubectl get modeladapter`. Status should be `bound` or `Ready`.
- **Validation**:
  - `kubectl get services` (Ensure adapter services exist).
  - `kubectl get httproute -n aibrix-system` (Ensure routes exist).

### Phase 2: Route Inspection
- **Objective**: Confirm the controller generated secure routes.
- **Action**: `kubectl get httproute <name> -n aibrix-system -o yaml`
- **Validation**:
  - Look for `rules.matches.headers`.
  - Ensure BOTH `model` AND `x-tenant-id` (or `x-aibrix-tenant-id`) are required.
  - *If `x-tenant-id` is missing, isolation is NOT active.*

### Phase 3: Traffic Simulation (The Test Script)
Use the provided `test-script.ps1` to simulate traffic.

#### Test Class A: "Happy Path"
- **Scenario**: Valid Tenant accesses their own model.
- **Request**:
  - Header `model`: `qwen-code-lora-tenant`
  - Header `X-Tenant-ID`: `tenant-a`
- **Expected Result**: 200 OK / Success response.

#### Test Class B: "Isolation / Hacker Test"
- **Scenario**: Malicious user tries to access Tenant A's model using a different Tenant ID.
- **Request**:
  - Header `model`: `qwen-code-lora-tenant`
  - Header `X-Tenant-ID`: `hacker-tenant`
- **Expected Result**: 404 Not Found or 503 Service Unavailable. (Request should NOT reach the model).

## 4. How to Run the Tests
1. **Port Forward** the Gateway (if running locally):
   ```powershell
   kubectl port-forward svc/envoy-aibrix-system-aibrix-eg-81cab807 -n aibrix-system 8095:80
   ```
2. **Execute the Script**:
   ```powershell
   .\samples\multitenancy\test-script.ps1
   ```

## 5. Troubleshooting
- **Result is "Success" for Hacker?**
  - The `HTTPRoute` is missing the Tenant ID match.
  - **Fix**: Check `ModelAdapter` labels. If controller fails to update, manually patch the `HTTPRoute` to add the `headers` match rule.
- **Result is "503" for Everyone?**
  - Check `Service` port configuration.
  - Ensure the Envoy Gateway can reach the Model Service (check EndpointSlice).
- **Result is "404" for Everyone?**
  - Check `path` in `HTTPRoute`. The script uses `/v1/completions`. Ensure the route covers this path.
